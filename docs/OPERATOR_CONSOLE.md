# 서버관리자(제작자) 모드 — 설계

2026-08-20. `docs/OPERATOR_APPROVAL.md` 에서 정한 **①③** 을 실제로 어떻게
만들지 적은 문서다.

> **2026-08-20 · 만들었다.** 아래 설계대로 넣었고, 보안규칙은 Firestore 에뮬레이터에서
> **52개 시나리오로 검증**했다(제작자가 명단·PIN·급여·재고를 못 읽는 것 포함).
> 새 화면 둘은 브라우저에서 26개 시나리오 통과.
>
> **쓰려면 콘솔에서 두 가지를 해야 한다.**
> 1. `firestore.rules` 를 다시 게시한다 (새 규칙이 들어 있다)
> 2. `admin.html` 을 열어 나오는 **기기 번호**를 콘솔 `operators` 컬렉션에 문서로 넣는다.
>    문서 ID = 그 번호, 필드 `name` 아무 값. **기기 두 대를 등록해 둔다**
>
> 개통 승인은 **꺼진 채로** 내보냈다. 켜기 전에는 예전과 똑같이 동작한다 —
> 쓰던 병원이 갑자기 막히면 안 되기 때문이다. 준비되면 `admin.html` 에서 켠다.

세 가지가 한 덩어리다 — **제작자 화면 · 구독 기한 · 비밀번호 분실.**
셋 다 보안규칙을 고쳐야 하고, 규칙은 콘솔에 손으로 올려야 하니 **한 번에 묶어서**
내보내는 게 왕복을 줄인다.

---

## 0. 먼저 풀어야 하는 것 — 지금은 병원이 하나로 고정되어 있다

`firebase-config.js` 의 `WORKSPACE_ID` 가 `"clinic"` 로 박혀 있다.
모든 데이터가 `hospapp/clinic` 아래 있다는 뜻이라, **병원이 둘이 되면 섞인다.**

병원마다 다른 주소를 갖게 하는 것이 선행 과제다. 방법은 두 갈래.

| | 어떻게 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| 주소에 붙이기 | `…/mediops-pilot/?h=posco` | 배포 하나로 끝 | 주소를 바꾸면 남의 병원이 보일까 — **규칙이 막으니 안 보인다.** 다만 주소가 지저분하다 |
| 병원마다 배포 | 병원별로 파일 복사 | 주소가 깔끔 | 고칠 때마다 전부 다시 배포. **하지 말 것** |

주소에 붙이는 쪽이 맞다. 처음 열 때 제작자가 병원 코드를 정해주고,
그 링크를 병원에 준다. 앱은 그 코드를 기억한다.

---

## 1. 제작자를 어떻게 알아보는가

**앱 안에 뒷문을 두지 않는다.** 잠김 복구 문과 같은 원칙이다.

- `operators/{uid}` 문서가 있으면 제작자다
- 이 문서는 **콘솔에서 한 번만** 만든다. 앱에서는 만들 수도 지울 수도 없다
- 규칙이 이 문서를 대조한다

제작자 기기도 **두 대**를 등록해 둔다. 하나를 잃으면 아무 병원도 못 열어준다.

---

## 2. 제작자가 할 수 있는 것과 없는 것

`docs/OPERATOR_APPROVAL.md` 의 ③ 을 그대로 지킨다.

| | 제작자 |
|---|---|
| 병원 목록 · 개설 신청 · 개통 승인 | 한다 |
| 구독 기한 늘리기 · 잠그기 | 한다 |
| 최고관리자 아이디·비밀번호 **초기화** | 한다 (아래 4장) |
| 직원 명단 · PIN · 인사기록 | **못 읽는다** |
| 급여 · 근로계약서 · 신청서 | **못 읽는다** |
| 재고 · 출퇴근 · 연월차 | **못 읽는다** |

화면에서 가리는 게 아니라 **보안규칙으로 막는다.**

### 화면은 따로 만든다

병원 앱(`index.html`)이 이미 350KB다. 제작자 기능은 병원 직원이 볼 일이
없으므로 **`admin.html` 을 따로** 둔다. 병원 앱을 건드리지 않으니 병원 쪽
안정성에 영향이 없다.

---

## 3. 구독 기한 — 승인만으로는 월 구독이 안 지켜진다

개설 승인은 **문을 열어줄 때 한 번** 작동한다. 한 번 열어주면 그 뒤로 계속 쓴다.
월 구독을 지키는 건 승인이 아니라 **기한**이다.

```
hospapp/{ws}/license/main
  paidUntil   언제까지 쓸 수 있나 (timestamp)
  plan        요금제 이름
  status      'trial' | 'active' | 'suspended'
  note        제작자 메모 (입금 확인 등)
```

- **제작자만 쓴다.** 병원은 읽기만 한다 — 남은 기간을 화면에 보여주려고
- 규칙에서 데이터 문서마다 `request.time < paidUntil` 을 조건으로 얹는다.
  **서버 시계**로 재기 때문에 폰 시계를 바꿔도 소용없다
- 무료 체험 30일 = `paidUntil` 을 30일 뒤로 찍는 것. 같은 장치로 끝난다
- 미납은 아무것도 안 해도 저절로 잠긴다

### 잠겨도 자료는 내줘야 한다

미납이라고 백업조차 못 받게 하면 분쟁이 난다. 남의 직원 근로계약서와 급여가
들어 있는 자료다. **잠기더라도 "내 자료 내보내기" 하나는 열어둔다.**
자료는 지우지 않고 잠그기만 하니, 입금되면 날짜만 미뤄도 그대로 살아난다.

---

## 4. 비밀번호를 잊었을 때 — 지금은 길이 하나뿐이다

**현재 상태가 위험하다.** 최고관리자 비밀번호를 잊으면 Firebase 콘솔에서
`recovery/open` 문서를 만드는 것 말고 길이 없다. 그런데 오늘 콘솔에 2단계
인증까지 걸렸으니 **구글 계정 비밀번호 + 폰**이 있어야 한다.
폰을 잃으면 백업 코드가 있어야 하고, 그것도 없으면 병원이 통째로 잠긴다.

**세 겹으로 만든다. 아래로 갈수록 최후다.**

### 1겹 · 관리자 기기 두 대 (이미 있다 · 가장 싸다)

비밀번호를 잊어도 승인된 기기가 살아 있으면 잠기지 않는다.
설정에서 아이디·비밀번호를 다시 정하면 끝이다.
**원장님과 실장님 기기 두 대를 승인해 두는 것**이 지금 할 수 있는 최선이다.

### 2겹 · 복구 코드 여덟 개 (새로 만들 것 · 권장)

아이디·비밀번호를 정할 때 **한 번 쓰는 코드 여덟 개**를 같이 만들어
인쇄·보관하게 한다. 구글 2단계 인증의 백업 코드와 같은 원리다.

- `ownerkey/main` 에 정답 하나 대신 **정답 + 코드 여덟 개의 늘린 값**을 둔다
- 규칙이 대조할 때 정답이든 코드든 하나만 맞으면 통과시킨다
- 코드로 들어오면 앱이 **곧바로 새 비밀번호를 정하게 하고, 코드도 새로 발급**한다.
  이렇게 해야 쓴 코드가 다시 안 통한다 (앱은 `ownerkey` 를 읽지 못해서
  코드 하나만 지우는 것은 불가능하다)
- **콘솔도 제작자도 필요 없다.** 병원이 스스로 푼다

### 3겹 · 제작자 초기화 (최후)

제작자가 그 병원의 `ownerkey` 를 지운다. 그러면 앱이 "아이디가 아직
등록되지 않았어요" 상태로 돌아가고, **전화번호 + PIN 으로 들어가 다시 정한다.**

> **정직하게 짚어둘 것.** 이걸 만들면 **제작자는 마음만 먹으면 어느 병원의
> 문이든 열 수 있다.** 기술로 막을 수 없다 — 문을 열어주는 사람이 문을 열 수
> 있는 건 당연하다. 그래서 이건 기술이 아니라 **기록과 계약**의 문제다.
>
> - 초기화하면 **로그가 남고, 그 병원 화면에도 보여야 한다** ("○월 ○일
>   제작자가 최고관리자 비밀번호를 초기화했습니다")
> - 위탁 계약서에 **제작자가 할 수 있는 일**로 적어야 한다
>   <span>근거 · 개인정보 보호법 제26조</span>

## 5. 자동결제 — 지금 만들지 않고, 나중에 끼울 자리만 잡는다

**결제는 서버가 있어야 한다.** 정기결제의 빌링키는 브라우저에 두면 절대 안 되는
값이라, 결제사를 붙이려면 Cloud Functions 같은 서버가 필요하다. 그건 상용화
단계 일이다.

그래서 지금은 **자리만** 잡는다. 핵심은 이것이다 —
**수동이든 자동이든 같은 칸을 갱신하게 만든다.**

```
hospapp/{ws}/license/main
  paidUntil        ← 이 칸 하나가 문을 여닫는다
  billing:
    provider       'manual' | 'toss' | …
    customerKey    결제사가 주는 식별값 (서버만 쓴다)
    status         'none' | 'ready' | 'active' | 'failed'
    lastPaidAt
    nextBillingAt
```

- **지금(수동)** — 계좌이체를 확인하고 제작자가 `paidUntil` 을 한 달 미룬다.
  `provider` 는 `manual`
- **나중(자동)** — 결제사 서버가 결제에 성공하면 같은 `paidUntil` 을 미룬다.
  앱과 규칙은 **한 줄도 안 고친다**

이렇게 해두면 결제사를 붙이는 일이 "앱을 바꾸는 일"이 아니라
"`paidUntil` 을 미뤄줄 주체가 하나 늘어나는 일"이 된다. 그게 **삽입만 하면 되게**
만들어 둔다는 말의 실체다.

병원 수가 적을 때는 수동이 오히려 편하다. 자동화는 손이 모자랄 때 한다.

---

## 6. 만드는 순서

1. **병원 코드 분리** (0장) — 이걸 안 하면 나머지가 의미 없다
2. **제작자 판별 + 규칙** (1·2장) — 콘솔 두 번 (규칙 게시 + 제작자 기기 등록)
3. **`admin.html`** — 병원 목록 · 개통 승인 · 기한 늘리기
4. **복구 코드** (4장 2겹) — 규칙을 2번에서 같이 올린다
5. 제작자 초기화 + 로그 (4장 3겹)
6. 자동결제는 자리만 (5장). 실제 연결은 나중에

**2번과 4번의 규칙 변경은 한 번에 묶어서** 올린다.
