# DB_MIGRATION.md — 나중에 다른 클라우드·DB 로 옮길 때 비용이 커지지 않게

**옮기기로 정한 것은 없다.** 클라우드도 정하지 않았다(2026-10-12 사용자 결정: "변수가 많은 상태라 미리 염두에 두고 작업하고,
정말 옮길 때 비용이 너무 들지 않게 사전에 막고 싶다"). 그래서 이 문서는 **이전 계획이 아니라 설계서의 재료**다 —
지금은 코드를 바꾸지 않고, ① 어디가 Firebase 에 닿아 있는지 ② 무엇이 이식되는 모양인지 ③ 무엇이 Firebase 에만 있는 기능인지를 못 박아 둔다.
이전이 정해지면 이 문서에서 시작한다.

## 1. 한 줄 요약

- **호스팅(버셀)**: 쉽다. 앱은 정적 파일 + 서버 함수 하나(`api/`). 함수의 핵심은 `api/_core.js` 에 서버 종류와 무관하게 분리해 두었다(`SERVER.md` 6장).
- **DB·인증·권한**: 이 앱에서 **제일 비싼 부분**이다. 브라우저가 Firestore 를 직접 부르고 `firestore.rules`(290줄)가 권한을 막는 구조라,
  다른 곳으로 가면 **그 규칙이 하던 일을 서버(API)가 대신해야 한다.** 코드를 옮기는 문제가 아니라 권한을 다시 만드는 문제다.
- 접촉면은 작은 편이다: 앱 상태가 전부 하나의 자료(`DB` JSON)이고, 저장은 몇 개의 문서로 나눠 올린다.

## 2. 이식되는 모양 (지금 이미 지켜지고 있는 것 — 지킨다)

1. **상태 전체가 `DB` 하나의 JSON** 이다. 백업 파일(`백업 저장`)이 곧 `DB` 라서, 어느 백엔드로 가든 이 JSON 하나로 옮길 수 있다. **`DB` 의 모양을 바꿀 때는 옛 모양도 읽게 한다**(`ensureSchema`).
2. **Firestore 전용 값을 안 쓴다**: `serverTimestamp`·`FieldValue`·트랜잭션·배치·서브컬렉션 질의가 없다(2026-10-12 점검). 값은 문자열·숫자·불리언·배열·객체뿐이다.
3. **문서 경로가 단순하다**: `hospapp/{병원}/{종류}/{문서}` 한 단계. 병원(`ws`) 별로 통째로 분리되어 있다.
4. **날짜는 문자열**(ISO)이다. DB 의 날짜 타입에 기대지 않는다.
5. **서버 함수의 핵심은 껍데기와 분리**되어 있다(`api/_core.js` ↔ `api/scan.js`), 앱의 서버 주소는 `scanUrl()` 한 곳이다.

앞으로 지킬 것: **Firebase 를 부르는 코드는 3장의 접촉면 함수 안에서만** 쓴다. 새 함수에서 `fdb`·`firebase.`·`.collection(`·`onSnapshot`·`ref…()` 를 쓰면
`test/DB접촉면.mjs` 가 실패한다 — 정말 필요한 것이면 그 시험의 목록과 이 문서 3장을 같이 고친다(조용히 퍼지는 것을 막는 장치다).

## 3. Firebase 에 닿는 함수 (접촉면, 2026-10-12 기준 43개)

`test/DB접촉면.mjs` 가 이 목록을 지킨다.

| 묶음 | 함수 | 하는 일 |
|---|---|---|
| 경로 만들기 | `wsRef` `refShared` `refRoster` `refSecrets` `refPeople` `refMeta` `refUsage` `refOwnerKey` `refUnlock` `refClaims` `refLicense` `refOpslog` `refResignInv` `refResignSub` | 문서·컬렉션 주소 |
| 연결·구독 | `cloudInit` `watchClaim` `watchRecovery` `watchLicense` `watchPendingClaims` `loadGateMeta` | 로그인(익명)·내 승인 상태·복구 문·구독 기한·승인 대기 구독 |
| 읽기·쓰기 | `writeAll` `cloudPushNow` `cloudPush` `migrateIfNeeded` `openData` | 저장(문서별 나눠 쓰기)·옛 단일 문서에서 이전·자료 화면 |
| 기기 승인 | `claimDevice` `cancelClaim` `approveClaim` `rejectClaim` `renderActiveClaims` `applyRole` | 기기 신청·승인·거절·역할 반영 |
| 로그인·개설 | `doLogin` `doOwnerLogin` `doRecoveryLogin` `doSetupAdmin` `explainSetupFail` `sendOpenRequest` `setOwnerKey` | 최고관리자 키·복구 코드·첫 관리자 개설·개설 신청 |
| 사직서 링크 | `openResignLink` `makeResignLink` `acceptResignSub` `openStaffHub` | 로그인 없이 내는 사직서(링크 발급·접수) |
| 사진 판독 | `scanCall` | 서버 함수를 부를 때 로그인 토큰(`firebase.auth().currentUser`)을 가져온다 |

**아쉬운 점**: 사직서 4개와 `openData`·`applyRole` 은 화면 함수가 DB 를 직접 만진다. 이전을 정하는 시점에 이 여섯 개를 "저장소 함수"로 빼면 접촉면이 깔끔해진다
(지금 하지 않는 이유: 에뮬레이터 시험 환경이 없어 저장·권한 쪽은 건드릴수록 위험하다).

## 4. 데이터 지도 — `hospapp/{병원}/…`

| 문서 | 담는 것 | 크기·모양 | 읽기 | 쓰기 |
|---|---|---|---|---|
| `shared/main` | 재고·임플란트(제품·규격·대장·이력)·출퇴근·연월차·공지·거래처·주문체크·병원 설정·급여 열쇠 정보 등 `B_SHARED` 의 23개 칸 | **한 문서에 다 들어간다**(Firestore 문서 1MB 한도에 닿을 수 있다 — 이전 때 오히려 풀리는 제약) | 승인된 기기 | 승인된 기기 |
| `roster/main` | 직원 명단(PIN 제외) | 작다 | 승인된 기기 | 관리자 |
| `secrets/main` | PIN·관리자 PIN·인사 기록·의무교육 기록 | 작다 | **관리자만**(직원 기기에 안 내려감) | 관리자 |
| `people/{직원}` | 계약서·급여명세서·신청서·사직서(**암호화된 본문**) | 직원당 하나 | 관리자 + 본인 | 관리자 + 본인 |
| `claims/{기기 uid}` | 기기 신청·승인 상태·역할 | 기기당 하나 | 본인 + 관리자 | 신청은 본인, 승인은 관리자 |
| `meta/main` | "이 병원에 사람이 있는가"(있다/없다만) | 아주 작다 | 로그인한 누구나 | 관리자·첫 개설 |
| `usage/main` | 계량기(직원 수 등 개수만) | 작다 | 로그인한 누구나 | 관리자 |
| `license/main` | 구독 기한·정지 상태(제작자만 씀) | 작다 | 로그인한 누구나 | **제작자만** |
| `opslog/*` | 제작자가 병원에 손댄 기록 | 누적 | 로그인한 누구나 | 제작자만 |
| `ownerkey/main` · `unlock/{uid}` | 최고관리자 아이디·비밀번호의 정답 / 앱이 적어내는 답안 | 작다 | **아무도 못 읽음**(규칙만 대조) | 관리자 / 본인(쓰기만) |
| `recovery/open` | 잠겼을 때 첫 관리자 문을 다시 여는 스위치 | 문서 하나 | 로그인한 누구나 | **콘솔에서만** |
| `resigninv/{토큰}` · `resignsub/{토큰}` | 사직서 링크 / 낸 사직서 | 건당 하나 | 토큰을 아는 사람 / 관리자 | 관리자 / 퇴직자(한 번만) |
| 병원 밖: `operators/{uid}` · `config/main` · `hospitals/{ws}` · `hospreq/{ws}` | 제작자 명부·전체 설정(개통 승인)·병원 명부·개설 신청 | 작다 | — | 제작자(콘솔) |

## 5. Firebase 에만 있는 기능에 기대는 곳 (이전 때 새로 만들어야 하는 것)

| 기대는 것 | 어디서 | 옮길 때 |
|---|---|---|
| **보안규칙이 곧 권한**(규칙 290줄) | 읽기·쓰기 전부 | 서버 API 가 같은 일을 해야 한다. 4장의 읽기·쓰기 열이 그 설계표다. 특히 "관리자만 읽는 문서가 직원 기기에 안 내려간다"가 앱의 약속이다 |
| **익명 로그인의 uid = 기기 신원** | `claims/{uid}`, 승인 흐름 전체 | 기기 토큰 발급·검증이 필요하다(익명 로그인이 없으면 대체 설계) |
| **규칙 안에서 다른 문서를 읽어 판단**(`get`/`exists`, 한 번에 10개까지) | 승인·역할·구독 기한·최고관리자 키 대조 | 서버가 같은 판단을 한다. 최고관리자 키 대조는 "앱은 정답을 못 읽고 서버만 안다"는 구조라 서버로 옮기면 오히려 단순해진다 |
| **서버 시계로 구독 기한 판단**(폰 시계로 못 속임) | `license` | 새 서버의 시계를 쓰면 된다 |
| **실시간 구독**(`onSnapshot` 10곳) | 승인 대기·복구 문·구독 기한·자료 갱신 | 실시간이 없으면 주기 조회(폴링)로 시작해도 앱은 돌아간다(알림이 몇 초 늦음). 웹소켓·SSE 면 그대로 |
| **오프라인 저장·재전송**(SDK 가 해 줌) | 병원에서 인터넷이 끊겨도 쓰는 흐름 | 서비스워커 + 로컬 저장으로 다시 만들어야 한다. 앱은 이미 `localStorage` 에 `DB` 를 저장한다 |
| **문서 한 개 = 한 번에 쓰기** | `shared/main` 통째 덮어쓰기(여러 기기가 동시에 고치면 마지막이 이김) | 새 DB 에서는 칸 단위 갱신으로 풀 수 있다(오히려 좋아짐) |

## 6. 이전이 정해지면 — 순서 초안

1. **무엇을 옮기나 결정**: 호스팅만(쉬움) / DB 까지(이 문서 4·5장). 클라우드가 정해지면 아래 **변수**를 확인한다.
2. **API 설계**: 4장의 표를 엔드포인트로 바꾼다(예: 병원 `shared` 읽기·쓰기, 직원 `people` 읽기·쓰기, 기기 신청·승인, 구독 조회). 권한 판단은 서버가 한다.
3. **저장소 함수로 모으기**: 3장 "아쉬운 점" 6개를 정리하고, 접촉면 함수 43개를 새 서버 호출로 바꾼다. **두 방식을 한 코드에 같이 두지 않는다** — 환경 하나로 정한다.
4. **데이터 이전**: 병원별로 백업 JSON(= `DB`)을 만들어 새 서버로 가져온다. 이전 전·후 `backupSummary` 숫자(재고·케이스·직원 수 등)를 맞춰 본다.
5. **시험**: 접촉면 시험을 새 구현에 맞게 고치고, 권한 시험(`test/rules.*.mjs` 가 지키던 것: 승인 안 된 기기·남의 급여·스스로 관리자 되기·구독 만료·복구 문)을 **새 서버에 똑같이** 건다.
6. **병행 기간**: 옛 방식을 읽기만 하는 기간을 둔다(롤백).

**클라우드를 정할 때 확인할 변수**: ① 병원 자료(건강·인사 정보)를 둘 **지역과 법적 요건**(국내 보관 여부) ② 실시간·오프라인 대안 ③ 인증 방식(익명 기기 신원을 어떻게) ④ 관리자만 읽는 문서의 분리 방법 ⑤ 비용 구조(읽기·쓰기 횟수 과금인지, 서버 상시 비용인지) ⑥ 한국에서의 속도 ⑦ 사진 판독 같은 서버 함수를 어디서 돌리는가 ⑧ 결제·구독 연동.

- 일부러 안 한 것: 저장소 추상화 계층 신설(두 구현 동시 유지·시험 비용), 다른 DB 시험 구현, `shared/main` 분할(실사용 부담이 생길 때).
