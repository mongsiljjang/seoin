# MediOps 로드맵 — 치과 운영·재고·노무 통합 SaaS

> 전국 치과가 **재고(임플란트 포함)·출퇴근·연월차·노무·거래처 발주**를 한 앱에서 관리하고,
> **벤더(오스템·네오 등)와 실시간으로 연동해 자동 발주**까지 이어지는 서비스.
> 설치형·고가의 기존 프로그램(예: 덴트웹) 대비 **카톡 링크 하나 · 무료 맛보기 · 실시간 공유**가 차별점.

_문서 버전 v0.1 · 최종 수정 2026-08 · 작성 기준: 현재 동작하는 파일럿 + 대표 인터뷰_

---

## 0. 한 줄 요약
**"위생사·실장의 반복 업무를 없애고, 원장의 재고·노무·세무 리스크를 줄이는 치과 운영 SaaS."**
핵심 3축 = ① 임플란트 재고 정합(입고·사용·실재고·오차) ② 벤더 실시간 연동 자동발주 ③ 노무 서류 통합.

---

## 1. 문제와 기회

**원장(의사결정자)의 고통**
- 실장 의존도가 크고, 실장 역량 편차·갑질·이직 리스크가 큼.
- 임플란트 재고 오차(장부 ≠ 실물), 페일·보험 사용 구분이 수기라 실사 때 곤란.
- **노무 분쟁**(사직서 미작성·급여명세서 미교부)이 세무보다 더 머리 아픔.
- 세무조사·보험 실사 시 거래명세서·세금계산서·기공의뢰서 자료 취합이 번거로움.

**위생사·실장(사용자)의 고통**
- 재고 실사·발주 누락, 반복 입력, 근태·연차 수기 관리.

**벤더(오스템·네오 등)의 고통**
- 병원 소진 속도를 몰라 주문 예측이 어려움 → 재고·영업 비효율.

**기회**
- 기존 솔루션은 비싸고 설치형·EMR 중심. **무료 맛보기 + 카톡 링크 + 실시간 + 벤더 연동**은 빈 시장.
- 위생사·실장 커뮤니티가 크고, "삶의 질을 높여준다"는 메시지로 자연 확산 가능.

## 2. 제품 개요 · 차별점

| | 기존(설치형/EMR형) | MediOps |
|---|---|---|
| 도입 | 설치·계약·교육 필요 | **카톡 링크 하나**, 설치 없음 |
| 가격 | 고가·연계약 | **무료 맛보기 → 단계 유료** |

| 발주 | 수기 전화·팩스 | **min 자동 발주서 → 벤더 실시간** |
| 노무 | 별도 서식 | **근로계약서·연월차·사직서·급여명세서 한 페이지** |

## 4. 목표 아키텍처 (상용 SaaS)

**설계 원칙** (상세: `docs/DATA_MODEL.md`)
1. **멀티테넌트**: 모든 데이터에 `hospitalId`, 병원 간 접근은 **보안규칙으로 강제 차단**.
2. **현재값 ≠ 진실의 원천**: 현재고·잔액은 캐시, **append-only 거래이력**이 원천(임플란트 대사가 이미 이 방식).
3. **삭제 금지 · 역거래**: 수정·삭제 대신 상태변경/보정 기록(감사 대비).
4. **금액은 정수(원)**, 통화 KRW 고정.
5. **감사로그**·시점 스냅샷 보존.

**역할(권한)**
- `super_admin`(운영사) · **원장/admin** · **실장/manager** · 직원 · **벤더(vendor)** — 벤더는 자기 담당 병원의 발주서만.

**인증·과금**
- 병원 가입(원장) → 직원 전화+PIN(내부 신뢰) · 벤더 계정(별도) · 요금제 결제.

**기술**
- 현재: 정적 웹(단일 HTML) + Firebase(Firestore/Auth) + GitHub Pages/Firebase Hosting.
- 확장: **Firestore 보안규칙**(테넌트 격리·역할·append-only) + **Cloud Functions**(발주·정산·급여계산 서버검증) + **Storage**(서류·사진) + **결제**(토스페이먼츠 등).

## 5. 벤더 자동발주 — 핵심 기능 설계

```
[병원]  재고 min 도달 → 자동 '발주서' 생성(권장수량)
                               │  실시간(Firestore)
                               ▼
[벤더]  오스템/네오 영업 앱에서 발주서 확인 → '출고' 처리
                               │
                               ▼
[병원]  '입고 확인' → 재고 자동 반영 + 임플란트 대사 갱신
```

- **안전장치(2단계)**: "자동 입고"를 무조건 반영하지 않고 **벤더 출고 + 병원 입고확인**으로 확정 → 오배송·미결제 사고 방지(대표 우려 반영).
- **권장 발주량**: min·최근 평균 소모·벤더 리드타임에서 산출(거래이력 기반).
- **벤더 정산 규칙(심화)**: 계약/미계약, **할당률·이월(전 재고로 잡기)**, **페일 분기 교환** 등은 별도 정산 모듈로. 영업사원 대상 운영 가이드 동반 필요.

## 6. 노무 · 세무 모듈 (원장 핵심 니즈)

- **노무 서류 한 페이지**: 근로계약서 · 연월차 · **사직서** · **급여명세서**를 직원별로 통합.
- **사직서 링크**: 링크 전송 → 직원이 개인정보 **동의 후 작성** → 자동 업로드. 미작성 시 **결근 처리 증거**로 활용.
- **급여명세서 배포**: 금요일 등에 직원이 **본인 것 다운로드**(법적 교부 의무 충족, "줬다/안 줬다" 분쟁 차단).
- **노무 증거**: 출퇴근·GPS·업무지시 공지 로그를 증거로 축적.
- **세무 자료 보관**: 거래명세서·세금계산서·의약품 거래명세표를 **사진으로 모아 보관**(노션/Storage 연동), 세무조사·보험 실사 시 즉시 제출.

> 원칙: 자료가 **투명하게 한 곳**에 쌓이면, 실장 개인 역량과 무관하게 원장이 직접 관리·확인 가능 → 실장 의존·리스크 감소.

## 7. 단계별 로드맵 (Phase)

| Phase | 내용 | 산출물 | 예상 |
|---|---|---|---|
| **0. 파일럿** | 재고·임플란트·근태·연차·실시간 | 현재 앱 | ✅ 완료 |
| **1. 멀티테넌트 토대** | hospitalId 격리 · 병원 가입 · 보안규칙 · 기존 데이터 '1번 병원'으로 이전 | 다병원 뼈대 | 2~3주 |
| **2. 거래처·자동발주** | 거래처·발주서 · 벤더 계정 · min 자동발주(2단계) | 벤더 연동 MVP | 3~4주 |
| **3. 실시간 소통** | 병원↔벤더 발주 채팅·알림, 공지사항(업무지시 로그) | 커뮤니케이션 | 2주 |
| **4. 노무 서류** | 근로계약서·사직서 링크·급여명세서 배포 | 노무 모듈 | 3~4주 |
| **5. 세무 자료** | 거래명세서·세금계산서 사진 보관·노션 연동 | 세무 아카이브 | 2주 |
| **6. 요금제·과금** | Free/Pro/VIP · 자동결제 | 수익화 | 2주 |
| **7. 분석·추천** | 소진 예측·추천 발주·리포트 | 인사이트 | 지속 |

_기간은 1인 개발 기준 대략치. 병렬·우선순위 조정 가능._

## 8. 요금제 (수익화 가설)

| 플랜 | 대상 | 포함 | 과금 |
|---|---|---|---|
| **Free(맛보기)** | 소규모 의원·원장 | 출퇴근·연월차·기본 재고 (1병원) | 무료 |
| **Pro** | 일반 치과 | 임플란트 대사·벤더 연동·엑셀·GPS·키오스크 | 월 구독 |
| **VIP** | 다지점·노무 민감 | 노무 서류·세무 보관·다지점·우선지원 | 월 구독(상위) |

- **판매 대상 = 실장이 아니라 원장.** 실장 업무 경감이 셀링 포인트지만 결제·도입 결정은 원장.
- 컨설팅사(연봉 실장 만들기 등) 대비 **가격·확산성**으로 경쟁. 무료 맛보기로 유입 후 전환.

## 10. Go-to-Market
- **무료 맛보기 유입** → Pro/VIP 전환(연차·근태부터 습관화).
- 원장 커뮤니티·강연·후기 → 자연 확산("실장 삶의 질↑" 메시지).
- **벤더 제휴**(오스템·네오): 발주 연동을 채널로 활용해 병원 확산.

## 11. 즉시 다음 스텝
1. **[보안 · 1순위] Firebase Auth 로 로그인 교체 + 문서 분리 + 보안규칙.**
   지금은 앱 데이터 전체가 Firestore 문서 하나에 담겨 모든 직원 기기로 내려간다. 권한은 화면에서 가리는 방식이고, **직원 PIN 이 그 안에 평문으로 들어 있다.** 급여·근로계약서는 임시로 브라우저 암호화(AES-GCM)로 막아 두었지만, 근본 해법은 이것이다.
   - 로그인을 Firebase Auth 로 바꾼다 (지금은 익명 로그인 + 클라이언트 PIN 대조)
   - 급여·계약서를 `payslips/{staffId}` 처럼 직원별 문서로 쪼갠다
   - 보안규칙으로 본인과 오너·인사담당자만 읽게 한다
   - 이걸 하면 급여 열쇠(사람이 외우는 암호)를 없앨 수 있다
2. 본 로드맵 확정(방향·우선순위).
3. **Phase 1(멀티테넌트 토대)** 착수 여부 결정 — 상용화의 뼈대라 먼저 잡는 것을 권장. 위 1번과 같이 간다.
4. 병렬로 Phase 2(벤더 자동발주) 프로토타입 → 데모로 원장·벤더 반응 검증.

> 파일럿(현재 앱)은 계속 실사용하며 피드백을 모으고, 위 Phase를 얹어 상용화로 전환한다. **기존 데이터는 유지·이전한다.**
