# AUTH_MIGRATION.md — 로그인·보안 교체 계획

> 상태: **계획 단계** (2026-08-19 작성) · 아직 코드 없음
> 결정: 카드 등록(Blaze)은 보류. 로그인 교체를 먼저 한다.

## 왜 해야 하나

지금 앱은 데이터 전체를 JSON 한 덩어리로 Firestore 문서 하나(`hospapp/clinic`)에 넣고, 모든 기기가 그걸 통째로 내려받는다. 권한은 화면에서 가리는 방식이다.

그래서 이런 것들이 못 지켜진다.

- **직원 PIN 이 공유 DB 에 평문으로 있다.** 조금 아는 직원은 남의 PIN 을 읽는다
- **급여·근로계약서**는 임시로 브라우저 암호(AES-GCM)로 막아 뒀지만, 사람이 열쇠를 외워야 하고 잊으면 못 연다
- **서류 파일**을 올릴 수가 없다. Storage 를 켜도 "본인 것만"이라는 규칙을 만들 수 없어서다

## 막혔던 지점 — 그리고 우회로

**Firebase Auth 로 그냥 바꾸면 관리자의 PIN 재설정 기능이 사라진다.** 남의 비밀번호를 바꾸는 건 Admin SDK(서버) 일이고, 재설정 메일은 직원의 실제 이메일이 있어야 간다. 둘 다 이 앱에 없다.

### 쓰기로 한 방법 — 기기 등록(device claim)

익명 로그인은 그대로 두고, **어느 기기가 누구인지**를 관리자가 승인해 문서로 못 박는다.

```
직원이 앱을 연다 → 익명 uid 발급
  ↓ 전화번호 + PIN 입력 (지금과 같음)
claims/{uid} = {staffId, approved:false} 로 신청
  ↓
관리자가 승인 → approved:true
  ↓
보안규칙이 request.auth.uid 로 사람을 가릴 수 있게 된다
```

- 서버가 필요 없다
- PIN 은 여전히 앱 로직이라 **관리자 재설정이 그대로 산다**
- 기기를 바꾸면 다시 승인받아야 한다 — 잃어버린 폰으로 못 들어온다
- 앱에 이미 "직원 승인" 개념이 있어 흐름이 낯설지 않다

## 데이터 구조 재설계

| 지금 | 바꾼 뒤 | 누가 읽나 |
|---|---|---|
| `hospapp/clinic` 에 전부 | `hospapp/clinic/shared/main` — 재고·출퇴근·연월차·공지·거래처·담당 | 승인된 모든 직원 |
| ″ | `hospapp/clinic/people/{staffId}` — 계약서·급여명세서·신청서·사직서 | 본인 + 오너·인사담당자 |
| ″ | `hospapp/clinic/claims/{uid}` — 기기 등록 | 본인(쓰기) · 관리자(승인) |
| ″ | `hospapp/clinic/roster/main` — 직원 명단(PIN 제외) | 승인된 모든 직원 |
| ″ | `hospapp/clinic/secrets/pins` | 오너·인사담당자만 |

## 단계 (한 번에 하지 않는다)

실사용 중인 데이터라 되돌릴 수 있게 나눠서 간다.

1. **백업 먼저.** 설정 → 전체 백업(JSON) 을 받아 따로 보관. 이게 안 되면 시작하지 않는다
2. **claims 컬렉션과 승인 화면**만 먼저 올린다. 기존 동작은 그대로 두고 병행
3. 모든 기기가 승인을 받은 것을 확인
4. **읽기를 새 구조로 옮긴다** — 쓰기는 아직 옛 문서에도 같이. 문제 생기면 되돌린다
5. 며칠 지켜본 뒤 **쓰기도 새 구조로**
6. **보안규칙을 건다.** 이 시점부터 화면이 아니라 서버가 막는다
7. 옛 문서 정리 · 급여 열쇠(사람이 외우는 암호) 제거 검토
8. 그다음에 Storage(카드 등록 후) → 서류 파일 업로드

## 되돌리기

각 단계마다 이전 단계로 돌아갈 수 있어야 한다. 4~5단계에서 양쪽에 같이 쓰는 이유가 그것이다. 6단계(규칙) 이후에는 규칙만 풀면 이전 동작으로 돌아간다.

## 주의

- **마이그레이션 중에는 두 저장소 index.html 동기화를 더 조심한다.** 한쪽만 새 구조면 데이터가 갈린다
- 규칙을 걸기 전에 **에뮬레이터나 테스트 workspace 로 먼저 확인**한다. 규칙이 틀리면 앱 전체가 멈춘다
