# 서버를 만든다 — 무엇을, 어디에, 어떤 순서로

2026-10-06. 지금까지 "서버가 있어야 한다"고 미뤄둔 것들을 한자리에 모으고,
어디에 어떻게 만들지 정한 문서다.

## 0. 왜 지금인가

하루 동안 서버 없이는 안 되는 것이 네 개 나왔다.

| 하고 싶은 것 | 왜 서버가 필요한가 |
|---|---|
| 카카오 로그인 | Firebase 가 카카오를 모른다. 카카오가 준 신분증을 Firebase 가 믿는 형태로 바꿔줄 중간 역할이 필요하다 |
| 알림톡·문자 | 보내는 열쇠를 브라우저에 두면 아무나 그 열쇠로 문자를 보낸다 |
| 이메일 | 같은 이유 |
| 자동결제 | 정기결제 빌링키는 브라우저에 두면 절대 안 되는 값이다 |

공통점은 하나다 — **브라우저에 두면 안 되는 비밀값을 누군가 대신 들고 있어야 한다.**
그게 서버다.

## 1. 어디에 만드나

| | 돈 | Firebase 요금제 | 비고 |
|---|---|---|---|
| **Vercel 함수** | 무료 범위로 시작 | **무료(Spark) 그대로** | 이미 계정이 있다 |
| Firebase Cloud Functions | 무료 범위 있음 | **종량제(Blaze) 전환 — 카드 등록** | Firestore 와 한 몸 |

**Vercel 을 권한다.** 카드를 안 꽂아도 되고, 계정이 이미 있다.
Firebase 는 무료 요금제를 그대로 두고, 서버만 밖에 두는 구조다.

> 앱 배포는 **GitHub Pages 그대로** 둔다. Vercel 은 앱이 아니라 **서버 함수만** 올린다.
> 주소가 둘이 되면 승인이 둘이 된다 — 오늘 겪은 그 문제다.

## 2. 순서

### 1단계 · 카카오 로그인  ← 가장 큰 효과

오늘 하루를 통째로 잡아먹은 문제가 이것으로 풀린다.
**신분증이 기기가 아니라 계정이 되면**, 폰을 바꾸든 저장이 날아가든 같은 사람으로 들어온다.
승인은 사라지지 않고 **사람당 한 번**으로 줄어든다.

서버가 하는 일은 딱 한 가지다 — 카카오가 "이 사람 맞다"고 하면,
Firebase 가 알아듣는 표를 하나 끊어준다.

### 2단계 · 알림톡 / 문자

- 직원이 사용 요청을 내면 실장에게 알림톡
- 재고가 최소에 닿으면 담당자에게 알림톡
- 승인 코드 발송

알림톡은 카카오 비즈니스 채널과 발신 프로필이 있어야 하고 **심사가 있다.**
심사 전에는 문자로 보낸다.

### 3단계 · 이메일

사직서 사본, 월 보고서처럼 기록으로 남겨야 하는 것.
급한 알림은 알림톡이 낫다 — 병원에서 메일함을 보는 사람은 거의 없다.

### 4단계 · 자동결제

구조는 이미 잡아뒀다(`docs/OPERATOR_CONSOLE.md` 5장).
결제사가 `paidUntil` 을 미루기만 하면 앱과 규칙은 한 줄도 안 고친다.
병원 수가 적을 때는 수동이 오히려 편하니 제일 뒤에 둔다.

## 3. 몽실쌤이 준비해야 하는 것

코드는 내가 쓰지만, 계정과 열쇠는 주인만 만들 수 있다.

**1단계(카카오 로그인)에 필요한 것**

1. **카카오 디벨로퍼스** 앱 등록 → REST API 키
2. 그 앱에 **사이트 도메인** 등록 (`https://mongsiljjang.github.io`)
3. **Firebase 서비스 계정 키** 발급
   (콘솔 → 프로젝트 설정 → 서비스 계정 → 새 비공개 키 생성)
4. 위 둘을 **Vercel 환경변수**에 넣기

**2단계(알림톡)에 필요한 것**

5. 카카오 비즈니스 채널 개설 + 발신 프로필 등록 (심사 기간 있음)
6. 문자 발송 업체 계약 (알림톡 심사 전 대체 수단)

## 4. 정직하게 짚어둘 것

**서버가 생기면 관리 책임이 생긴다.** 지금까지는 비밀값이 아예 없었다 —
보안규칙 하나가 전부였고, 그래서 털릴 것도 없었다.
서버가 생기는 순간 **서비스 계정 키와 결제 열쇠를 들고 있게 된다.**
그 열쇠가 새면 병원 전체가 열린다.

그래서 서버는 **쓰는 만큼만** 만든다. 기능을 서버로 옮기지 않는다 —
브라우저에 둘 수 없는 값만 서버가 들고, 나머지는 지금처럼 앱과 규칙이 한다.

**서버는 공짜가 아니다.** 지금은 고장 나도 내 브라우저만 멈춘다.
서버가 생기면 고장이 전 병원에 동시에 간다. 로그와 되돌리기를 같이 만들어야 한다.

## 5. 서버 없이 되는 길도 남아 있다

로그인 문제만 놓고 보면 **전화번호 문자 인증**으로도 같은 효과가 난다.
Firebase 가 기본으로 지원해서 **서버가 필요 없고, 무료 요금제 그대로**다.
이 앱은 이미 직원을 전화번호로 구분하고 있어서 잘 맞는다.
드는 돈은 문자값뿐이고, 직원이 한 번씩만 받는다.

**카카오 로그인이 꼭 필요한 이유가 "익숙함" 하나라면**, 문자 인증으로 먼저 가보고
불편하면 그때 카카오를 붙이는 쪽이 싸다. 서버는 2단계(알림톡)부터 만들어도 늦지 않다.


## 6. 사진 판독(LLM) — 2026-10-07 추산·결정

> **구현 상태 (2026-10-12, 사용자가 "수첩 사진 올리기를 넣자" 고 해서 만들었고, 같은 날 여러 길을 열어 두도록 넓혔다 — 키는 아직 안 넣었다)**
> - 서버 함수 `api/scan.js`(버셀이 `api/` 폴더를 그대로 함수로 올린다) · 앱의 `📝 수첩 → ✍️ 글로 붙여넣기 / 📷 사진으로 올리기` · LOT 칸 옆 `📷` · 시험 `test/사진판독.mjs`
> - **두 가지 일**: ① 수첩 사진 → 수첩 줄 → 확인 표 ② 상자·라벨 사진 → LOT·REF·유효기한(환자 정보 없음). LOT 는 먼저 **폰·브라우저의 바코드 읽기**(GS1: (10)LOT (17)유효기한)를 쓰고, 안 되면 AI(라벨 모드), 그것도 안 되면 직접 적게 한다.
>   바코드 읽기는 `BarcodeDetector`(크롬 등)가 있으면 그걸, 없으면(사파리) 필요할 때만 `@zxing/library` 를 jsDelivr 에서 불러온다 — **이 경로는 실제 바코드로 시험하지 못했다.** 오스템·메가젠 상자의 바코드가 GS1 인지는 샘플 사진으로 확인해야 한다
> - **AI 서비스는 둘 중 고른다**: Google Gemini(기본 모델 `gemini-2.5-flash`) · Anthropic Claude(`claude-sonnet-5-5`). 키가 오는 길은 둘이고 **요청의 "내 키"가 먼저**다.
>   ① **내 키(병원 키)** — 병원이 자기 키를 만들어 수첩 화면의 `내 AI 키로 쓰기` 에 넣는다. 키는 그 **기기의 localStorage 에만** 저장되고, 사진을 읽을 때만 서버 함수에 함께 실려 간다(함수는 저장도 로그도 하지 않는다). **요금은 키 주인에게 간다 → 운영자는 요금도 키 보관도 맡지 않는다.** 공용 PC 에는 넣지 말라고 화면에 안내했다. 서버에는 키가 없어도 된다
>   ② **서버 키** — 운영자가 버셀 환경변수 `GEMINI_API_KEY` 또는 `ANTHROPIC_API_KEY` 를 넣는다(`SCAN_PROVIDER` 로 고름). 사용자별 하루 5장 임시 한도가 걸린다
> - **구글 무료 키 주의**: 무료 등급은 보낸 내용을 구글이 서비스 개선에 쓸 수 있고 사람이 읽을 수도 있다(구글 약관, 2차 요약 기준 — 현재 약관은 ai.google.dev 에서 확인). AI Studio 로 쓰면 결제를 연결해도 무료로 취급된다는 설명도 있다. **이름·차트번호가 보이는 수첩 사진은 유료 키로, 무료 키는 이름을 가린 사진으로만** 쓰도록 화면에 적었다. 무료 일일 허용량은 출처마다 달라(100~1,500회) 구글 AI Studio 화면에서 직접 본다
> - 흐름: 앱이 사진을 긴 변 1600px JPEG 로 줄여 보낸다 → 함수가 사용자 토큰으로 Firestore 공유 문서를 읽어 보며 직원인지 확인한다(보안규칙이 허락해야 통과 — **내 키가 있어도 직원이어야 한다**, 남의 요금으로 쓰는 열린 문이 되지 않게) → AI 가 읽는다 → 수첩이면 서버가 이름을 한 번 더 가리고(성·끝 글자만 남김) 전화·주민번호처럼 보이는 숫자를 지워 앱의 **수첩 확인 표**로 넣는다. 확인 표를 거치기 전에는 재고에 반영되지 않는다
> - **사진은 저장하지 않고 로그에도 남기지 않는다.** 다만 **사진 자체는 AI 서비스(회사)로 전송된다** — 이름이 전부 적힌 수첩이면 이름이 그대로 간다. 유료(API) 약관의 보관·학습 정책을 확인하고 병원에 알려야 한다(안내 문구는 화면에 넣었다)
> - **켜려면 사용자 손이 필요하다**: (내 키 방식) 병원 PC/폰에서 aistudio.google.com(구글 로그인)으로 키를 만들어 수첩 화면에 붙여넣는다 · (서버 키 방식) 콘솔에서 키를 만들고 **월 지출 상한**을 건 뒤 버셀 → Settings → Environment Variables 에 넣고 다시 배포한다. 키가 하나도 없으면 앱은 꺼진 것으로 안내하고 글 붙여넣기는 그대로 된다
> - **한도는 임시**: 서버 키의 사용자별 하루 5장은 서버가 다시 뜨면 0 으로 돌아간다. 병원별로 믿을 수 있는 한도(`license.maxScanPerDay`)와 월 지출 상한은 아직 아니다 → 서버 키를 쓴다면 콘솔의 월 지출 상한이 진짜 안전장치다
> - **정확도는 아직 모른다.** 환자 이름을 가린 수첩 사진 15~20장과 상자·라벨 사진으로 줄별 오독 수를 세는 시험이 필요하다(아래 시험 계획). 서비스·모델은 환경변수로 갈아 끼울 수 있다
> - 병원별 키를 **서버에 안전하게 보관**하는 것(직원 폰에 키가 내려가지 않게)은 Firebase 관리자 권한이 필요한 별도 작업이라 하지 않았다 — 병원이 여럿이 되면 한다

> **별도 서버로 옮길 때 (구독제 전환 · 사용자 결정 2026-10-12: 구독제로 넘어가면 키는 운영자가 만든다 — 자세한 것은 그때 의논)**
> 옮기기 쉽게 **핵심과 껍데기를 나눠 두었다.**
> - `api/_core.js` — 서비스 호출(Gemini·Claude) · 프롬프트 · 이름 가리기 · 줄/라벨 정리 · 직원 확인 · 한도. **서버 종류와 상관없다**(파일 이름이 `_` 로 시작해 버셀이 주소로 열지도 않는다). 계약은 파일 맨 위에 적었다:
>   `handle({ method, body, env }) → { status, json }`
> - `api/scan.js` — 버셀 껍데기(10줄). 요청을 `handle()` 에 넘기고 응답으로 돌려줄 뿐이다. **새 서버에서는 이 파일만 그 서버 방식(Express·Cloud Functions 등)으로 다시 쓴다**
> - 앱은 서버 주소를 `scanUrl()` 한 곳에서만 만든다. 서버를 다른 주소로 옮기면 `firebase-config.js` 옆에서 `window.SCAN_API_BASE = "https://새서버"` 만 채우면 된다(그 서버는 앱 주소의 요청을 받도록 CORS 를 열어야 한다)
> - 옮길 때 같이 손볼 것: ① 한도(`overLimit`)를 메모리가 아니라 DB 로 ② 직원 확인(`isMember`)을 관리자 SDK 의 토큰 검증으로 바꿔도 된다 ③ 병원별 키를 서버가 보관하게 하려면 Firebase 관리자 권한이 필요하다 ④ 월 지출 상한·사용량 기록
> - 시험 `test/사진판독.mjs` 의 8번 묶음이 "핵심에 버셀 코드가 없다 · 껍데기가 얇다 · 핵심만으로 계약이 지켜진다 · 서버 주소가 한 곳이다" 를 지킨다

수첩을 하루 한 장 사진으로 올린다)이 이 앱에서 LLM 이 필요한 **유일한** 자리다. 폐기가 아니라 보류다
