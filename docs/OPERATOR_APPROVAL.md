# 제작자(서버관리자) 승인 구조 — 결정과 범위

2026-08-20 결정. 갈래 셋 중 **①③** 으로 간다. 지금은 만들지 않는다.

## 무엇을 만드는가

병원이 새로 문을 열 때 **제작자가 승인해야 열리게** 한다. 지금은 아무나
앱 주소만 알면 `관리자 만들기` 로 병원을 열 수 있다. 병원이 하나일 때는
문제가 아니지만, 남에게 팔기 시작하면 개통을 통제할 방법이 있어야 한다.

## ① 언제 만드는가 — 앱에 들어간 뒤

지금 순서로는 **사용자가 앱에 못 들어가고 있는 것이 먼저**다. 문이 안
열리는데 문을 하나 더 다는 셈이 되고, 지금 만들면 콘솔에 두 번 더 가야
한다(규칙 게시 + 제작자 기기 등록). 진입이 확인되고 규칙이 게시된 뒤에
착수한다.

## ③ 무엇까지 볼 수 있는가 — 개통과 승인만

제작자 계정은 **병원을 열어주고 닫는 것까지만** 할 수 있다.
병원 안의 데이터는 못 읽는다.

| | 제작자가 보는가 |
|---|---|
| 병원이 있다·없다, 개설 신청, 개통 상태 | 본다 |
| 직원 명단(`roster`) | 못 본다 |
| PIN·인사기록(`secrets`) | 못 본다 |
| 급여·계약서·신청서(`people`) | 못 본다 |
| 재고·출퇴근·연월차(`shared`) | 못 본다 |

**화면에서 가리는 게 아니라 보안규칙으로 막는다.** 로그인한 사람에게
통째로 내려주고 화면에서 가리던 옛 방식이 이번 교체의 이유였다 —
같은 실수를 제작자 계정으로 되풀이하지 않는다.

## 왜 지금 나눠두는가

안 나누면 제작자 계정이 **모든 병원의 급여와 PIN 을 볼 수 있게** 된다.
원장 본인 병원 하나면 아무 일도 아니지만, 다른 병원을 받는 순간 남의
직원 개인정보를 대신 맡아 보관하는 관계가 된다. 그러면 계약서에 "무엇을
어디까지 볼 수 있는지"를 적어야 한다(개인정보 보호법 제26조가 말하는
위탁 계약이다). **나중에 쪼개는 것보다 처음부터 안 보이게 만드는 것이
훨씬 싸다.**

## 만들 때 손댈 곳 (착수 전 메모 — 설계는 그때 확정한다)

- 제작자를 어떻게 알아보는가 — 기기 등록 한 번(콘솔)으로 못 박고, 규칙이
  그 문서를 대조한다. 앱 안에 뒷문을 만들지 않는다(잠김 복구 문과 같은 원칙)
- 개설 문을 어디서 막는가 — 지금은 `noClinicYet()` 이 "명단이 비었으면
  누구나" 로 열려 있다. 여기에 제작자 승인 문서를 조건으로 얹는다
- 제작자가 실수로 잠그면 어떻게 푸는가 — `recovery/open` 과 같은 최후 수단
- 병원이 여럿이 되면 `hospapp/{ws}` 의 `ws` 가 병원 구분이 된다. 지금은
  `clinic` 하나로 고정되어 있다(`firebase-config.js`)
