# Session Handoff — 2026-08-20 · MediOps

로그인·보안 교체를 **한 세션에 다 했다.** `docs/AUTH_MIGRATION.md` 의 8단계를 그대로 따르지 않고 접었다 — 앱에 실제 데이터가 없다는 게 세션 중에 밝혀졌기 때문이다.

> **지금 사용자가 앱에 못 들어가고 있다.** 그게 이 문서에서 가장 중요한 사실이다. 6장과 7장 1번을 먼저 읽는다.

## 1. 세션 목표와 완료 결과

목표는 "로그인·보안 교체 1단계(백업)". 실제로는 **8단계 전부 + 원래 계획에 없던 것 셋**을 했다.

| 한 일 | 상태 |
|---|---|
| 백업·복구 보강 (1단계) | 배포됨 |
| 데이터를 넷으로 쪼개기 (2~5단계) | 배포됨 |
| 기기 등록·승인 | 배포됨 |
| 보안규칙 (6단계) | 코드 배포됨 · **콘솔 게시는 옛 버전** |
| 잠김 복구 문 (계획 없던 것) | 코드 배포됨 · 콘솔 미게시 |
| 최고관리자 아이디·비밀번호 (계획 없던 것) | 코드 배포됨 · 콘솔 미게시 |
| `baton` 스킬 ChatGPT 판 + 묶기 스크립트 | `mongsiljjang/skills` 에 |

**데이터 구조가 바뀌었다.** 예전엔 전부를 `hospapp/clinic` 문서 하나에 넣고 로그인한 사람에게 통째로 내려줬다. 이제 넷이다.

```
shared/main     재고·출퇴근·연월차·공지     승인된 직원 모두
roster/main     직원 명단 (PIN 없음)         승인된 직원 모두
secrets/main    PIN·인사기록                 최고관리자·인사담당자
people/{직원}   계약서·급여·신청서·사직서    본인 + 관리자
claims/{기기}   이 기기가 누구 것인지        본인 · 관리자가 승인
meta/main       "사람이 있는가" 만           로그인한 누구나
recovery/open   잠김 복구 스위치             콘솔에서만 생성
ownerkey/main   최고관리자 비밀번호 정답     **아무도 못 읽음**(규칙만)
unlock/{기기}   비밀번호 답안                **아무도 못 읽음**
```

직원 폰은 자기 `people` 문서 하나만 구독한다. 남의 급여는 화면에서 가려지는 게 아니라 **아예 안 내려온다.**

## 2. 결정과 근거

- **8단계를 접고 한 번에 갔다.** 사용자 확인 결과 앱이 비어 있고 직원 계정도 전부 테스트용이었다. 2~5단계(병행 운영·며칠 지켜보기)는 살아 있는 데이터를 지키려던 장치라 지킬 게 없으면 비용만 남는다. **데이터가 들어가기 전에 끝내는 게 가장 싸다** — 이 판단은 `AGENTS.md` 와 `docs/AUTH_MIGRATION.md` 에도 적었다
- **Firebase 에 남는다.** 사용자가 대안을 물어 조사했다. 고치려던 문제(PIN 평문·남의 급여 내려옴)는 Firebase 탓이 아니라 문서 하나에 몰아넣고 화면에서만 가린 설계 탓이라 옮겨도 그대로 뚫린다. Supabase·Appwrite 는 카드 없이 파일 저장이 되지만 그건 Storage 하나 문제고, 그것도 요금이 아니라 카드 등록이다
- **최고관리자는 아이디·비밀번호로 어느 기기에서든 바로 들어간다.** 사용자 요구 — 실장이 원장을 대신하는 일이 잦다. 처음엔 뒷문이 된다고 반대했지만 실제 운영이 그렇다면 그게 우선이다. **대신 앱은 정답을 모른다** — 아이디·비밀번호를 PBKDF2 25만 회로 늘린 값만 `unlock` 에 적고, 맞는지는 보안규칙이 `ownerkey` 와 대조한다. 규칙의 `get()` 은 앱 권한과 무관하게 읽으므로 앱이 못 읽는 문서와 맞춰볼 수 있다. 틀려도 아무 말이 없어 한 번에 한 번씩만 물어볼 수 있다
- **강제 로그인을 앱에 넣지 않았다.** 누구나 쓸 수 있는 뒷문이 된다. 잠겼을 때 나올 길은 **콘솔에 들어갈 수 있는 사람만** 열 수 있는 `recovery/open` 문서로 했다
- **콘솔 작업을 최소화한다**(사용자 요구 — 잘못 건드리면 큰일 난다). 최고관리자 아이디·비밀번호가 생기면서 콘솔 갈 일이 사실상 없어졌다. `recovery` 는 비밀번호까지 잊었을 때만 쓰는 마지막 수단
- **규칙에서 모든 필드를 기본값과 함께 읽는다.** 없는 필드를 그냥 읽으면 규칙이 터지고, 터진 규칙은 무조건 거절이라 이유를 알 수 없다. 게다가 목록 읽기는 문서 하나만 이상해도 통째로 막힌다
- **`baton` 을 ChatGPT 판으로도 만들었다.** 같은 원리, 다른 작동 방식 — ChatGPT 는 명령을 못 돌리므로 실측을 사용자가 붙여넣고, 안 주면 "미확인"으로 적는다. 가장 위험한 실패가 "실측 건너뛰기"에서 "없는 걸 지어내기"로 바뀌기 때문

## 6. 열린 질문 · 위험 · 미룬 일

- **[막고 있음 · 최우선] 사용자가 앱에 못 들어간다.** 마지막 상태: 최고관리자 로그인 → "아이디가 아직 등록되지 않았어요"(정상 — 계정을 이 기능보다 먼저 만들었다). 이어서 전화번호+PIN 로그인도 **"안 들어가져"**. **어떤 화면·문구가 나왔는지 확인 못 하고 세션이 끝났다.** 다음 세션의 첫 일은 상태 확인이지 코드 수정이 아니다
- **실서버 데이터가 어떤 상태인지 모른다.** 사용자가 콘솔에서 `roster`·`shared` 컬렉션을 지웠고, 그 뒤 `clinic` 문서에 옛 `db` 필드만 남은 것을 스크린샷으로 봤다. 그 뒤 무엇이 생겼는지는 확인 못 했다
- **콘솔 규칙이 옛 버전이라 새 기능이 안 돈다.** 최고관리자 로그인·복구 문은 규칙을 게시해야 작동한다. 다만 **게시 전에도 기본 로그인은 되어야 한다** — 안 되고 있다면 다른 원인이다
- **어제 배포한 판이 사고를 냈다.** 승인 안 된 기기에서도 옛 자료를 새 구조로 옮기게 되어 있어, 사용자가 앱을 여는 순간 `roster` 가 만들어졌고 그러면 서버가 "이미 연 병원"으로 보아 아무도 첫 관리자가 될 수 없다. 그 길은 막았지만 **이미 만들어진 명단은 콘솔에서 지워야 풀린다**
- **낙관적 쓰기 경합** — 앱이 서버 확인 전의 자기 기기 등록을 보고 데이터를 요청하면 거절당하고, **거절당한 구독은 다시 살아나지 않는다.** 고쳤지만(서버 확인분만 신뢰 + 재연결) 같은 함정이 다른 곳에 또 있을 수 있다
- **최고관리자 비밀번호를 잊으면** `recovery/open` 을 콘솔에서 만들어야 한다. 앱 로그인 화면 → "아무도 못 들어갈 때" 에 절차가 있다
- **관리자 기기를 두 대 승인해 두는 것**이 이 모든 사고를 막는 가장 싼 방법이다. 아직 안 했다
- **검증 도구가 저장소에 없다.** 스크래치패드는 세션이 끝나면 사라진다
- `wrap` 과 `baton` 이 둘 다 살아 있다 · `baton` 이 세 곳(원본·사본·계정 스킬)에 있고 계정 스킬은 자동으로 안 따라온다
- 앞 핸드오프들의 위험은 그대로 — 급여 열쇠 분실 시 복구 불가 · 퇴사자/신입 동명이인 · Storage 카드 보류 · 연차 차감이 병가까지 합산 · deslop-ko 잔여 3건 · 앱 안 외부 링크 2개 미확인

## 7. 다음 작업 (우선순위)

1. **사용자를 앱에 들여보낸다.** 코드부터 고치지 말고 **상태를 먼저 잰다.**
   - 앱이 최신인지: `F12` → Console → `typeof gateOwnerHtml !== 'undefined'`
   - 무슨 문구가 뜨는지 그대로 받는다
   - 콘솔 데이터 탭에 `hospapp/clinic` 아래 무엇이 있는지 (`roster` 가 있으면 그게 문을 잠근 것 — 지우면 풀린다)
   - `관리자 만들기` 로 새로 시작하는 게 가장 빠르다. 앱이 비어 있으므로 잃을 게 없다

3. **관리자 기기 두 대 승인** — 원장·실장, 또는 폰·PC
4. **실서버에서 전 과정 한 번** — 최초 개설 → 직원 신청 → 승인 → 자료 수신 → 최고관리자 로그인
5. **검증 도구를 저장소로 옮긴다**(`test/` 같은 곳). 규칙을 고칠 때마다 필요하다
6. 그 뒤: Storage(카드) → 서류 파일 업로드 · 진단서 · 급여 열쇠 제거 검토
